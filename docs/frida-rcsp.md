# تحديد الـ fd الذي يحمل RCSP عبر Frida (مراقبة سلبية)

**الهدف:** معرفة أي واصف ملف (file descriptor) داخل تطبيق oraimo الرسمي يحمل نقل JieLi RCSP فعليًا — أي مقبس SPP/RFCOMM القناة 10 — وذلك **بالمراقبة فقط**، دون أن نرسل أو نحقن بايتًا واحدًا إلى السماعة.

> هذه تجربة من جهة **الأندرويد** (نراقب ما يفعله التطبيق الرسمي)، مكمّلة لتجربة btsnoop في [`next-experiment.md`](next-experiment.md). كلاهما سلبي. الوكيل على Linux لا يزال لا يفتح القناة ولا يصادق عليها ولا يكتب إليها.

## لماذا Frida؟

من التحليل الثابت ([`jieli-rcsp-apk.md`](jieli-rcsp-apk.md)) نعرف أن التطبيق يتصل عبر
`createRfcommSocketToServiceRecord(uuid)` ثم يكتب بـ `socket.getOutputStream().write()`.
لكن رقم القناة يأتي من SDP وقت التشغيل، والـ UUID يُضبط عند تهيئة المكتبة. لتأكيد **أي مقبس**
يحمل الإطار `FE DC BA … EF` أثناء التشغيل الحقيقي، نراقب استدعاءات المقابس في العملية ونطابق
البايتات مع مفكّك الغلاف المُثبت.

## المتطلبات

- هاتف Android عليه root و`frida-server` يعمل، وتطبيق oraimo مثبّت.
- على محطة العمل: `pip install frida-tools`، وكابل USB، وتفعيل تصحيح USB.
- ملفات هذا المشروع: `tools/frida_rcsp_probe.js` و`tools/frida_capture.py`.

## الأمان (لماذا هذا لا يُرسِل شيئًا)

`tools/frida_rcsp_probe.js` **مراقب فقط**:

- يستخدم `Interceptor.attach` فقط، ولا يستخدم `Interceptor.replace` أبدًا (لا يغيّر سلوك أي دالة).
- يقرأ محتوى المخازن في `onEnter`/`onLeave` لدوال `write`/`read`/`send`/`recv`/`sendmsg`/`recvmsg`، ولا يستدعي أيًّا منها بنفسه.
- خطّاف Java على `BluetoothSocket.connect` **ينفّذ `connect` الأصلي للتطبيق كما هو**، ثم يقرأ حقل الـ fd الخاص فقط (قراءة، لا كتابة).
- لا يمكن للنص أن يجعل التطبيق يرسل بايتًا لم يكن سيرسله أصلًا.

اختبار `tests/test_rcsp_fd.py::test_probe_script_is_passive_no_injection` يحرس هذا: يفشل إذا ظهر `Interceptor.replace` أو أي استدعاء إرسال داخل النص.

## الخطوات

1. شغّل `frida-server` على الهاتف، ووصّل USB.
2. **الالتقاط** (يولّد ملف NDJSON):

   ```bash
   # إما إطلاق التطبيق تحت المراقبة من البداية (يلتقط تسلسل الاتصال):
   python tools/frida_capture.py --spawn com.transsion.oraimosound -o rcsp.ndjson
   # أو الربط بتطبيق يعمل:
   python tools/frida_capture.py --attach oraimo -o rcsp.ndjson
   ```

3. داخل التطبيق، نفّذ عمليات **قراءة فقط** (افتح صفحة حالة السماعة، اقرأ الإصدار). تجنّب تحديث البرنامج الداخلي وإعادة الضبط.
4. أثناء التشغيل يطبع السكربت كل مرة يظهر فيها المؤشر `FE DC BA` مع الـ fd الحامل له، بالإضافة إلى fd الذي رصده خطّاف Java لمقبس RFCOMM.
5. أوقف بـ Ctrl-C. تُطبع النتيجة تلقائيًا: **أي fd يحمل RCSP**، وعدد الإطارات، والاتجاهات، والرموز.

## التحليل دون جهاز

النتيجة تُحسب بنفس الشيفرة في الحالتين، فيمكن إعادة تحليل أي التقاط محفوظ لاحقًا دون هاتف:

```bash
python tools/frida_capture.py --analyze rcsp.ndjson
```

هذا يستدعي `agent.rcsp_fd.identify_rcsp_fd`، الذي:

- يعيد تجميع بايتات كل `(fd, اتجاه)` على حدة (الإطار لا يعبر اتجاهين).
- يستخرج الإطارات الكاملة بـ `agent.sniffer.rcsp_extract` ويفكّ الغلاف بـ `decode_rcsp_frame` (نفس المفكّك المُثبت؛ محتوى `DATA` يبقى خامًا).
- يرتّب الـ fd حسب عدد الإطارات الصحيحة، ويعطي verdict فيه `rcsp_fd` و`confidence` وقائمة المرشحين وبقية الـ fd التي حملت حركة بلا إطارات RCSP.

**تمييز مهم:** ظهور البايتات `FE DC BA` في مخزن لا يكفي؛ لا يُحتسب الـ fd إلا إذا نتج عنه إطار كامل صحيح (طول متطابق وتذييل `EF` في موضعه). fd يظهر فيه المؤشر بلا إطار صحيح يُدرَج في `other_fds` مع `magic_seen: true` فقط.

## صيغة سجل الالتقاط (NDJSON)

سطر JSON واحد لكل مخزن مرصود يحمل المؤشر:

```json
{"t": 12.34, "fd": 47, "dir": "tx", "target": "socket:[123456]", "hex": "fedcba…"}
```

- `dir`: ‏`tx` كتابة (تطبيق → سماعة)، `rx` قراءة (سماعة → تطبيق).
- `target`: ناتج `readlink(/proc/self/fd/<fd>)` إن توفّر، لتأكيد أنه مقبس.

## ماذا بعد

- بعد تثبيت الـ fd، يمكن ربط الإطارات الملتقطة بجدول الأوامر (لا يزال ناقصًا: `com.jieli.bluetooth.constant.Command` وصيغة `AttrBean`)، وتوثيق ما يظهر تحت «محتمل» في [`protocol-status.md`](protocol-status.md).
- تبقى سياسة المشروع: لا إعادة إرسال ولا مصادقة ولا كتابة إلى القناة قبل فهم البنية كاملة.
